# Packet 05: Boundary Cases — typed boundary model, example generator, executed-test linkage, coverage map

Read `.handoff/packets/00-architecture.md` (binding) and `.handoff/stress-test-findings.md`. Build on `src/core/`; additive helpers only. This is the hard core of the Boundary Cases capability.

## Goal
For every requirement that names a numeric or domain limit, carry the smallest cases just below, at and above that limit, link each to an executed test, reject contradictory units, and export a coverage map that names every untested boundary. A requirement whose tests only exercise the happy path is NOT proven at its boundaries even if those tests pass.

## Scope
1. `src/boundary/model.rs`: typed `Bound { quantity: String, kind: Numeric{ value: Decimal-like (i128 scaled or f64 with exact decimal string kept), unit: Unit, op: Lt|Le|Gt|Ge|Eq|Range{lo,hi,inclusive flags}, step: smallest increment for the unit/type, integer: bool } | Domain{ allowed: Vec<String>, closed: bool } }`. `Unit` families with conversions: time (ms, s, min, h, d), size (B, KB, MB, GB with 1000 vs 1024 stated explicitly per fixture: use KiB/MiB for 1024), count (items, chars, lines, retries, files), percent. Serialized into the annotation layer's `bounds` section (tighten `$defs/bound` in `contracts/living-spec-annotations-v1.schema.json`).
2. Parser `parse_bounds(text) -> Result<Vec<Bound>, BoundaryError>` for plain-English phrasings: "at most N u", "no more than", "up to", "at least", "more than", "fewer than", "less than", "under", "over", "exactly", "between A and B (inclusive|exclusive)", "within N u", "N or fewer", "one of a, b, c" (domain), "only X, Y or Z" (domain). Phrasings it cannot parse with confidence return `NeedsAnnotation` (never a guess); an explicit `bounds` entry in annotations.json always wins over parsing.
3. `src/boundary/gen.rs`: below/at/above examples per bound using the unit step (integer counts: N-1, N, N+1; decimals: the declared step; time ms: ±1 ms; ranges: both edges each below/at/above; domains: each allowed value plus one nearest-invalid value e.g. a case/whitespace variant and an unlisted value). Each example states the expected outcome (accepted/rejected) derived from the op.
4. Unit contradiction: each boundary case links to an executed test via `{ position: below|at|above|edge-lo-…, value, unit, test_id }`. A test link declares the unit it exercises (`unit` field, or inferred from a literal suffix in the test body such as `_ms`, `Duration::from_millis`, `ms`, `* 1000`); if the declared/inferred unit's family matches but the numeric value only lines up after a scale mismatch (e.g. requirement 30 s, test uses 30 with unit ms) → `UnitContradiction` error naming both. Different families (seconds vs bytes) → error too.
5. `src/boundary/coverage.rs`: given bounds, links and test outcomes → `CoverageMap { requirement, bounds: [ { bound, cases: [ { position, value, expected, test_id?, status: tested_pass|tested_fail|untested } ] } ] }`; implement the core's boundary-gap provider (requirement ids with any case not `tested_pass`). Export JSON (schema `contracts/living-spec-boundary-coverage-v1.schema.json`, draft 2020-12, validated in tests with a minimal in-crate validator for the subset used OR by structural deserialization with `deny_unknown_fields` — state which) and a readable Markdown table export that lists every untested boundary by name, never collapsing them.
6. **Reference set:** `living-spec/tests/fixtures/boundary/requirements/` with exactly **30** original synthetic requirement fixtures (one JSON each: requirement text, expected parsed bounds, generated cases, executed-test links with outcomes). Mix: ≥10 time, ≥6 size, ≥8 count, ≥3 domain, ≥3 ranges; include ≥3 happy-path-only fixtures (a passing test only at a mid value), ≥2 unit-contradiction fixtures (expected rejection), ≥2 `NeedsAnnotation` phrasings resolved by explicit annotation.
7. CLI `living-spec boundary gen <spec-dir>` (write generated cases into annotations), `living-spec boundary coverage <spec-dir> --results <file> --format libtest|junit [--md out.md] [--json out.json]` (exit 3 if any boundary untested).

## Out of scope
Dependency or quantifier logic; per-domain rules beyond the unit families above.

## Acceptance
```sh
cd living-spec && cargo fmt -- --check && cargo clippy --offline --all-targets -- -D warnings && cargo test --offline
cargo test --offline boundary_reference_set -- --nocapture   # reports 30/30
```
Required tests: `boundary_reference_set` loads all 30, asserts parsed bounds and generated below/at/above cases equal each fixture's expectations, and that every case is linked or reported untested; `unit_contradiction_rejected` (seconds requirement tested in ms); `happy_path_only_is_not_proven` (passing mid-value test → coverage lists below/at/above as untested and the core badge becomes `unproven` with reason `boundary_gap`); coverage JSON validates against its schema; Markdown export names every untested boundary.

## Contract revisions that apply
R6 overrides scope item 4's inference: a bare number or name suffix like `_ms` does NOT establish a unit. Only authored link `unit` metadata or typed constructors (`Duration::from_millis`, `from_secs`, `timedelta(seconds=)`) count. Otherwise the case is `untested` with reason `unit_unknown`. MB and MiB are different scales. Among the 30 fixtures, include rejection/NeedsAnnotation phrasings: 'fast', a percentile, 'normally', negation, relational bounds, a disjunction, a date, a locale number ('1.000'), ambiguous 'between', and compound units. Parse the documented literal forms only.
